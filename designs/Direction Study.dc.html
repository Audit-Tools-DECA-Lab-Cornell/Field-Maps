Riverside Play Study · behaviour mapping

Direction study

Journeys, the five decisions that shape the product, three visual directions on the same map-plus-form screen, and the one selected. Variable codes and display-logic notes are read from Variables to use for App testing.xlsx; nothing in the protocol has been reinterpreted.
01 — Journeys

Three users, three different shapes of work

Each journey has one thing it must never get wrong. For the observer that is not losing an observation; for the manager it is not changing the meaning of records already collected; for the analyst it is knowing which records are actually in the database. The interface is organised around those three guarantees rather than around a feature list.

Field observer · phone & tablet

Prepare → round → place → answer → save → next

  1. Download the project package before leaving; verify it component by component.
  2. Start or resume a round; confirm observer, zone, and round context once.
  3. Place a point where the play event is — not where the tablet is.
  4. Answer only the questions the display logic reveals.
  5. Save to the device, see it written, continue immediately.

Critical decision: the round context screen is a separate, deliberate step. Weather, wind, shade and the zone inventory are round-scoped in the library (Climate1–3, LP Inventory 1–14), so they are asked once per round and shown as a locked header afterwards — never mixed into the per-event form.

Manager / PI · desktop web

Configure → preview → publish a version

  1. Set up site, zones and subzones, rounds, and observer assignments.
  2. Prepare and validate the map package; see what failed and why.
  3. Search the variable library, select questions, set display rules.
  4. Preview on phone and tablet frames at real size.
  5. Publish as an immutable form version; prior records stay bound to theirs.

Critical decision: publishing is versioned and additive. A new version never rewrites the interpretation of collected records; the review table always shows which version produced a row.

Analyst · desktop web + QGIS

Filter → inspect → flag → connect

  1. Coordinated map and table over one filter set.
  2. Open a record and see its full answer set plus context snapshot.
  3. Work through data-quality flags, not decorative charts.
  4. Read the same rows from QGIS over a live connection.

Critical decision: there is no “send to QGIS” action. QGIS connects to the same store and refreshes its layer. Exports exist for analysis and backup, and are labelled as such.

02 — Decisions

Five consequential design decisions

Decision 01
Scope is visible, not implied

Every answer is labelled with where it lives: project, observer, round, zone, or event. Changing round or zone shows an explicit list of what carries forward and what resets, before it happens.

Decision 02
Offline readiness is a checklist, not a thumbnail

Imagery tiles, site layers, form version, and zone/round reference data each report their own state and byte size. A project is “ready offline” only when all four verify.

Decision 03
Connectivity ≠ sync

Five record states — saved on device, waiting, syncing, synced, needs attention — each with an icon and a word. “Synced” appears only after the server acknowledges that revision.

Decision 04
Hidden answers are declared, never guessed

When a parent answer changes and children hide, the form says what happened to those values and stores them as not applicable — distinct from a configured “No” and from unanswered.

Decision 05
Four palettes that cannot collide

Map categories, marker states, sync states, and validation each draw from a reserved set. Status always carries an icon and a label, so nothing depends on colour alone.

04 — Selection

A — Survey Sheet

Chosen on four grounds, in order of weight for these users.

  1. Daylight. A light technical ground at near-white luminance is the most readable surface on a tablet held outdoors; dark themes fail here first.
  2. Semantic headroom. The accent is a single desaturated steel. Amber, green and red stay entirely unused by the chrome, so sync and validation states own them outright — the exact problem that rules out Field Rule.
  3. Density. Condensed headings and a 0.85× spacing scale fit long variable names and a 40-question instrument without truncation or a second scroll axis.
  4. Identity. Registration marks, hairline frames and square corners read as survey drawing. It looks like field science, not like a SaaS dashboard.

Night Transit is not discarded. It becomes the low-light theme — same layout, same components, dark tokens — scheduled after the primary theme is validated, per your note.

The four reserved palettes

Chrome & interaction
steel only — lines and marks at 500, filled controls at 800/900 so white type clears 4.5:1
Sync state
device · waiting · syncing · synced · attention
Map categories
desaturated site fills
Markers
shape codes play type; fill codes sync; white halo holds over aerial imagery

Marker shape carries the research category and marker fill carries the record state, so neither depends on hue. Every status chip in the product pairs a glyph with a word.

Honest about the prototype

Map rendering in these samples is a simulated vector site plan, not a georeferenced package. Download progress, sync attempts, server acknowledgement and conflict detection are scripted front-end states. No authentication, no PostGIS, no QGIS connection exists behind any screen. The interactive collector labels each simulated behaviour where it occurs.
