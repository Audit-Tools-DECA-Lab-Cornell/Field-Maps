# Contracts shared by web, mobile and API

This file is part of the [FieldMaps production plan](README.md) and defines the `CON-*` tasks. It is the single reference for:
- the shapes that cross a component boundary;
- the API endpoint catalog;
- the canonical form definition;
- the observation envelope;
- the error envelope.

Backend tasks in [backend/PLAN.md](../../backend/PLAN.md) implement these shapes. Web tasks in [web/PLAN.md](../../web/PLAN.md) and mobile tasks in [mobile/PLAN.md](../../mobile/PLAN.md) consume them. If a shape must change, change it here first, then update every task that consumes it. The `cross-repo-contract-change` skill describes the procedure.

## Context: why contracts are needed now

Today the mobile form format and the server form format disagree:

| | Mobile (`mobile/src/forms/definition.ts`) | Server (`backend/src/fieldmaps_api/forms.py`) |
|---|---|---|
| Question key | `id` | `code` |
| Kind names | `kind: one \| many \| text \| number` | `type: choice \| multi-choice \| integer \| …` |
| Range names | `min` / `max` | `minimum` / `maximum` |
| Conditions | `dependsOn` conditions | none |
| Hidden required fields | optional | rejected when missing (`forms.py:50-55`) |

API types are also written by hand twice: `web/src/lib/packages.ts:17-37` and `mobile/src/sync/contracts.ts`. And the `janet-test-v1` form cannot upload.

## The `contracts/` folder (repository root)

It holds language-neutral JSON only, with no shared JavaScript or Python package. Each app keeps its own dependencies, as `docs/Workspace.md` requires.

```
contracts/
  README.md                       rules below, who generates and who consumes each file
  openapi.json                    generated by BE-04; never edited by hand
  form-definition.schema.json     generated from mobile zod (CON-02); never edited by hand
  forms/<code>.json               canonical form definitions (hand-maintained, reviewed)
  forms/cases/<code>.cases.json   answers → expected visible question ids + errors
```

## Canonical form definition

**The mobile format is canonical.** It already carries versioned questions, `act` groups, restricted declarative conditions (`answered | equals | notEquals | includes | all | any`), dynamic option sets, `exportColumn`, provenance, and validation for duplicates, dangling references and cycles.

Rules both sides must implement identically:
1. **Answers are keyed by question `id`.** `exportColumn` is used only for GIS and exports.
2. **Visibility.** A question is visible when its condition holds over the current answers. Answers to hidden questions are dropped before saving.
3. **Required.** A question is required only while it is visible.
4. **Types.** `number` answers are JSON numbers (the mobile code currently stores strings, `mobile/src/domain/observation.ts:38`). `one` answers are an option code. `many` answers are an array of distinct option codes. `text` answers respect `maxLength`.
5. **Workbook rule text** is provenance only and is never executed.
6. **`status`** now lives on the server row (`form_versions.state`, DB-09), not inside the definition. The definition's own `status` field is ignored once DB-09 lands.

## Observation envelope (sync upload and storage)

```json
{
  "id": "uuid (client-generated)",
  "project_id": "uuid",
  "site_id": "uuid",
  "form_version_id": "uuid",
  "zone_code": "A | null",
  "package_version": 3,
  "longitude": -76.485, "latitude": 42.448,
  "observed_at": "2026-10-02T14:03:11.412-04:00",
  "observer_code": "JS",
  "answers": { "<question id>": "value" },
  "device_id": "uuid", "app_version": "1.0.0 (42)"
}
```

The current `PUT /v1/projects/{p}/observations/{uuid}` body (`site_id`, `form_version` code, `coordinates`, `observer`, flat answers) is accepted until MOB-10 ships, and is removed after the pilot.

## Error envelope

```json
{ "error": { "code": "membership_required", "message": "Human sentence.", "details": {} } }
```

**Codes** (extend this list here before using a new one): `unauthenticated`, `token_invalid`, `membership_required`, `role_required`, `not_found`, `conflict`, `validation_failed`, `limit_reached`, `rate_limited`, `invitation_invalid`, `invitation_expired`, `sole_owner`, `storage_unavailable`, `internal`.

`validation_failed` carries `details.fields: [{ "id": "<question id or field>", "problem": "…" }]`.

### `POST /v1/sync/upload` semantics

These follow PowerSync's guidance: <https://docs.powersync.com/handling-writes/writing-client-changes.md>.
- **Request:** `{ "operations": [ { "op": "PUT|PATCH|DELETE", "table": "observations", "id": "uuid", "data": { …envelope } } ] }`.
- **Commits.** Every accepted operation is committed **synchronously** before the response. Identical replays are accepted: the existing fingerprint logic in `backend/src/fieldmaps_api/repository.py:56-105`.
- **Validation, permission and conflict failures** return **200**. The response carries a per-operation result `{ id, status: "accepted|rejected", code }`, and the payload is written to `fieldmaps.upload_rejections` (DB-10), which syncs back to the user. Returning 200 keeps the client queue from blocking.
- **401** when the token is invalid; the client refreshes and retries.
- **5xx or 503** only for transient faults; the client retries.
- v1 accepts only `PUT` on `observations`. Any other table or operation is rejected with code `unsupported_operation`.
